# ACP 过程文本在工具调用前分段

## 现象与证据

会话 `session-1dd9d898-7267-421b-aee4-1eb88098fc2f` 的第 57 回合（2026-10-29
10:07:31–11:43:18，Asia/Shanghai）执行大量工具后，末尾出现一大段过程文字，接着才是最终答复。

对照 DSH 的 `session.v4.jsonl.zstd` 与 Codex rollout：

- 此回合有 312 个 `tool/call`，包括 164 个 bash、136 个 think、6 个 async_task、4 个 read 和 2 个遥测卡。
- Codex 发出 46 条 commentary 和 1 条 final_answer；DSH 中的正文串联后与之逐字一致。
- 正文与思考增量分别从 10:07:40、10:07:59 开始到达。过程文字在工具执行中间已生成，并非最后才生成。
- DSH 最后一个 assistant/message 包含 46 个 text、45 个 reasoning 内容块；最终答复只有 308 个字符。

历史解释中的“只有 Codex 的标题摘要、DSH 无需修复”不足以解释此现象。
这里既有 reasoning 摘要，也有 commentary 过程说明；两者需要按工具边界保持原来的展示顺序。

## 原因

ACP 网关把整个外部回合装进一次原生模型请求。工具公告、调用和结果单独实时写入；
思考与正文走流式通道，最后汇成同一个 assistant/message。

原有流没有在工具开始时封口；宿主又按 step 保留一个 assistant 展示节点。
因此只改变文本块编号，或同一步多写几个 assistant/message，都不能完整解决界面排序：
前者仍是一条大消息，后者可能被同一步的最后一条消息覆盖。

## 修复

1. 收到一个工具调用的首帧时，先关闭当前文本块。该调用的后续更新、结果不会再次截断文字；
   后来的同类增量也必须使用新块编号。网关和 preset 流使用同一边界约定。
2. 工具公告的 `message.source.replayState.response.threadharborAcpBoundary` 保存版本及
   `beforeBlock`（工具之后的下一块编号）。这是宿主允许的 adapter 私有回放元数据，
   不改工具参数或正文。文本与工具来自不同通道，同一毫秒甚至反序到达时，界面仍能按块编号分组。
3. 客户端在原生 Chat builder 上做展示投影：工具前的 reasoning 与 commentary 封成一个过程段，
   放在该工具之前；之后的文字进入下一段。原生工具卡、普通模型消息继续使用原渲染器。
4. 旧会话没有明确边界，用原有 stream 时间记录与工具事件恢复顺序，并逐字校验正文、思考总量。
   时间戳同毫秒的旧记录存在排序精度限制；缺少完整 stream 或校验不符时保留原消息，不隐藏内容。

原始会话文件与模型历史不改写。全回合是否折叠仍由 DSH 的“工作步骤展示”设置控制；
展开后各过程段与工具保持交错顺序。这里只展示 agent 已输出的内容，不补造思考文本。

## 验证

- 回归覆盖首次工具边界、同类型文本继续、重复更新、结果与遥测不重复截断、同毫秒跨通道反序、
  历史回放、缺少 stream 的保留路径、停止与重试、原生 renderer 委托及卸载恢复。
- 用本机 DSH reference 的真实 ConversationNodeAssembler、ChatSnapshotBuilder 和过程分组器
  离线回放第 57 回合：得到 141 个过程段；尾部只剩 30 字符的最后一条 reasoning 摘要及
  308 字符的最终正文；全部正文与思考逐字保留。
- 合并前隔离工作树类型检查、2109 个测试（41 跳过）和完整构建通过。
- 合并后主工作区有另外一项正在进行的未提交修改：当次全仓复检中，`cancel.spec.ts` 的
  dialect 测试替身缺少 `readReplyUsage` 导致类型检查失败，`plugin.spec.ts` 的连接自愈用例失败。
  本修复没有修改这些文件。客户端单包编译及产物验证已通过，`lib/client.js` 已更新；
  不把这一结果写成主工作区全仓门禁通过。
- 部署检查还发现主工作区 `node_modules/@threadharbor` 的五条软链指向另一工作树，
  已按 AGENTS.md 恢复到主工作区对应包，防止重启后加载旧代码。
- 桌面重启应用后加载新代码。未替用户重启桌面，避免中断其他会话。
