# 2026-10-20 · 主会话在等子代理时被总上限按「超时」收尾：子会话还在跑，主会话先报了错

## 问题描述

用户反馈：有子会话还在运行，但主会话报了超时——这不合理。

现场是桌面版 DSH（`~/.dsh`）里两个会话，当时的主会话模型已被用户切到
`acp:acp-zcode / GLM-5.3`：

- `session-7165a323-7364-42b8-bc2a-cba7b7aa7e7d`
- `session-fc642f4f-9231-449b-8b2e-7bb37d1e6717`

## 现场证据

- 报错的回合从 `turn/start` 到错误收尾**精确 1 800 000 ms**（网关总上限
  `totalMs` 的默认值 30 分钟），错误码 `ACP_TIMEOUT`，文案「外部 agent 回合超过
  总上限 1800000ms，已自动停止并重开新会话」。
- 同一回合里，codex 派出过 5 个子代理（`subagent` 卡片，参数形如
  `{"prompt":"Delegated task for Connector design","agent":"Connector design"}`），
  父回合一路用状态轮询工具（`status":"inProgress"`）等它们，**等了 26~28 分钟**。
  回合被上限掐断的那一刻，这 5 个子代理一个都没有收尾帧——日志里它们的 `tool/call`
  没有配对的 `tool/result`，只留下「工具调用已记录、结果未落盘，结果未知」。
- 也就是说：上限到点时外部 agent 还在等自己的子代理、还在上报，子代理仍在跑，
  父回合却被按「超时」杀掉并丢弃了外部会话，5 个子代理的结果全部丢失。
- 同一时刻界面上的子会话（批次二 `f1d1b274`）还在跑（19:34:46 → 19:51:41），
  主会话挂着一条红色超时横幅——用户看到的就是「子会话还在跑，主会话报超时」。

## 根因分析

- 位置：`packages/dsh-preset-dispatch/src/gateway.ts` 的**总上限**（`totalMs`）。
- 总上限当时是**墙钟**：交付时挂一次 `setTimeout`，之后不再重置，与外部 agent
  有没有动静无关。它要兜的是「怎么都不结束」的回合。
- 但外部 agent 派子代理、等子代理是正常的工作形态：父回合开着，子代理在跑，
  父回合还在持续上报（codex 每 50~97 秒轮询一次）。这段「一直很忙」的等待被
  算成了墙钟时间，30 分钟一到就把「还在等、还在报」说成「卡住了」，还顺手杀掉
  外部会话——子代理的结果随之丢失。

## 修复方案

- **总上限不再是墙钟，而是「最多连续安静多久」**：每来一次活动（外部 agent 的
  任何一帧——包括子代理的帧、文字流、工具事件）就重新计时。一直在忙的回合不会
  因为跑得久而被掐掉；真正安静下来（一条都没有）满上限才收场。
- **静默看门狗恢复原样**（`stallMs`，默认 120 秒无任何信号即收场）。中途试过
  给它也加「等子代理时让路」，但量过日志之后否掉了：我们跑的 agent 组合里
  没有出现过「父会话安静地等子代理」这种形态（见下），不为没发生的场景加戏。
- **委托运行的计数只进消息**：runner 逐帧记下外部 agent 还有几个子代理/
  后台任务没收尾，这个数不参与任何判定，只在收场时写进错误文案——「还有 2 个
  委托运行未收尾」，让「为什么停了」一眼能看懂是卡在等子代理还是自己卡死。

## 我们实际跑的 agent 会不会「安静地等子代理」

量了最近 40 个会话（按同一回合内相邻事件的最大间隔）：

| 谁派的子代理 | 父回合等它多久 | 等的过程中最长安静 | 撞上 120 秒静默期限？ |
|---|---|---|---|
| codex（外部 agent 自己的子代理） | 1598 / 1660 / 1680 秒 | 90.6 / 96.7 / 96.4 秒 | 没有（差 23 秒） |
| 宿主自己的子代理工具（GLM-5.3、minimax 的 `subagent`/`delegate_skill`） | 0 秒（后台派发，立即返回） | — | 父回合压根不等 |

所以：外部 agent 等子代理时并不安静，宿主侧的子代理工具又是后台派发——这个形态
在当前 agent 组合里没有出现过。真正需要修的是墙钟上限本身。

## 验证步骤

- 新增网关测试「总上限不是墙上时钟：一直有上报的回合跑过上限也不死」——
  **修复前是红的**（旧实现 20 秒就把还在上报的回合掐了）。
- 新增网关测试「总上限到点：连续静默满上限才收场」——总上限重新变成
  「连续静默多久」，用一条完全安静的回合验它到点收场（错误码仍是 `ACP_TIMEOUT`，
  仍带诊断包、仍丢弃会话、下一请求重开）。
- 新增网关测试「收场消息带上未收尾的委托运行」。
- 原有「静默看门狗」「totalMs=0 不限」「三类强制收场统一丢弃」等用例保持通过。
- 全仓 `npm run typecheck` + `npm run test`（1874 个用例）通过。
