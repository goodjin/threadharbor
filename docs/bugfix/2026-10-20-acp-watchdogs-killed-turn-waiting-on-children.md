# 2026-10-20 · 主会话在等子代理时被看门狗按「超时」收尾：子会话还在跑，主会话先报了错

## 问题描述

用户反馈：有子会话还在运行，主会话却报了超时——这不合理。

现场是桌面版 DSH（`~/.dsh`）里两个 GLM-5.3 会话：

- `session-7165a323-7364-42b8-bc2a-cba7b7aa7e7d`
- `session-fc642f4f-9231-449b-8b2e-7bb37d1e6717`

两个会话当时的主会话模型是 `acp:acp-zcode / GLM-5.3`（用户在 19:32–19:33
从 `acp:acp-codex / gpt-6-astra` 切过来），报错的回合本身跑在 **codex** 上。

## 现场证据

- 报错的回合从 `turn/start` 到错误收尾**精确 1 800 000 ms**（网关的总上限
  `totalMs` 默认 30 分钟），错误码 `ACP_TIMEOUT`，文案「外部 agent 回合超过总上限
  1800000ms，已自动停止并重开新会话」。
- 同一回合里，codex 派出过 5 个子代理（`subagent` 卡片，参数形如
  `{"prompt":"Delegated task for Connector design","agent":"Connector design"}`），
  父回合一路用状态轮询工具（`status":"inProgress"`）等它们。回合被上限掐断的
  那一刻，这 5 个子代理**一个都没有收尾帧**——日志里它们的 `tool/call` 没有配对的
  `tool/result`，只留下「工具调用已记录、结果未落盘，结果未知」。
- 也就是说：上限到点时外部 agent 还在等自己的子代理，子代理仍在跑，父回合却被
  按「超时」杀掉并丢弃了外部会话，5 个子代理的结果全部丢失。
- 同一时刻界面上的子会话（批次二 `f1d1b274`）还在跑（19:34:46 → 19:51:41），
  主会话挂着一条红色超时横幅——用户看到的就是「子会话还在跑，主会话报超时」。

## 根因分析

- 位置：`packages/dsh-preset-dispatch/src/gateway.ts` 的**总上限**（`totalMs`）
  与**静默看门狗**（`stallMs`）——两个看门狗都是「外部 agent 不出活」的兜底。
- 总上限是「一个回合最多跑多久」的绝对上限：交付时挂一次 `setTimeout`，不重置。
  它的本意是给「怎么都不结束」的回合兜底（`ACP_TIMEOUT` 与 `ACP_STALLED`
  同族，见 `docs/bugfix/2026-10-16-answer-deadline-killed-live-turns.md`）。
- 但外部 agent 在自己的回合里派子代理、等子代理，是**正常的工作形态**：
  父回合挂着不动，子代理在跑。等子代理的这段时间被算进了父回合的预算，
  30 分钟一到就把「还在等」说成「卡住了」，并且顺手把外部会话杀掉——
  子代理的结果随之丢失，主会话只剩一条超时横幅。
- 静默看门狗是同一族的另一个口子：连接安静满 120 秒就收场。父会话在等一个
  「安静干活」的子代理时，连接可以长时间没有帧，这时它同样把「还在等」
  说成「卡死了」。当天 19:31 会话 `b5ae2df8` 的那次静默收场**没有**子代理在跑
  （是真卡死），所以那一例不动；但「等子代理时被静默收场」这条路是通的。
- 这一层此前完全不知道「外部 agent 正在等自己的子代理」这件事：
  runner 已经在逐帧记账 spawned 运行（子代理 / 后台任务），
  但那份账本只用于补卡片，没有交给网关。

## 修复方案

- runner 逐帧记下还开着的委托运行（`liveDelegatedRuns()`）：出生帧记一笔，
  收尾帧销掉；两条路径（网关路径、接管路径）都在记。
- 会话诊断（`diagnostics()`）多带一个 `liveDelegatedRuns`。
- 网关的**总上限**据此让路：外部 agent 还有委托运行在跑时，**上限的钟停住**，
  等的那段时间不算这一回合自己的预算；子代理收尾后按**剩下的预算**继续。
  预算没被花掉，所以这一回合仍然有它自己的上限。
- 网关的**静默看门狗**同样让路，但留一个上限：容忍到「一个回合自己的预算」
  那么多（总上限关掉时取默认 30 分钟）。**这个上限从最后一次信号起算**——
  子代理只要还吐东西，静默的钟就重新开始，所以它不是「等一个固定时间」，
  而是「最多连续安静多久」。子代理真卡死时兜底仍在（一直不报才收场）；
  子代理收尾后换回原来的静默期限。

## 验证步骤

- 新增网关测试：总上限到点时外部 agent 还在等子代理 → 不收场、不丢弃会话；
  子代理收尾后按剩下的预算收场（错误码仍是 `ACP_TIMEOUT`）。
  该用例在修复前是红的（上限先到点把回合收掉）。
- 新增网关测试：静默看门狗到点时外部 agent 还在等子代理 → 让路一次，
  超过让路上限仍没信号才按 `ACP_STALLED` 收场。该用例在修复前是红的。
- 新增网关测试：子代理每 100ms 报一次东西时，5 秒里一次都不该被收场——
  容忍上限从最后一次信号起算（按累计让路时间的做法，这里 2s 处就把还活着的
  等待掐掉了）。该用例在按累计计的版本上也是红的。
- 新增 runner 测试：出生帧记一笔、收尾帧销掉。
- 原有「总上限到点按错误收尾」「totalMs=0 不限」「静默看门狗」等用例保持通过。
- 全仓 `npm run typecheck` + `npm run test`（1875 个用例）通过。
