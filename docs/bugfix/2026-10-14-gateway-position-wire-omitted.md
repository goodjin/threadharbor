# 2026-10-14 · 原地回答首航崩在 turn：网关与目录适配器之间的位置字段没接线

## 问题描述

用户在已开始的会话里选 Codex 的模型发第一条消息，回合失败：

> 本轮运行失败 Cannot read properties of undefined (reading 'turn')

同一次重试里换选 zcode/GLM-5.3 又报 `fetch failed`——两个错误，两条链。

## 现场证据

- 会话事件日志：第一轮 `request/context provider=acp:acp-codex model=gpt-6-astra`，
  流里只有一个 error finish，消息即 reading 'turn'；没有任何内容块——崩在发出
  提示之前。
- 运行器在回合开始就绑定卡片簿记，其中读 `turn.position.turn`；网关把
  `request.position` 原样塞进回合上下文。
- 目录适配器调用网关时构造的请求对象里根本没有 `position` 字段——依赖类型上
  也没写这个字段，编译器无从提醒。
- 第二轮 `fetch failed` 的现场：provider 是 `acp:acp-zcode`。zcode 此前已被
  改造为"直连 GLM 的模型插件"（不走外部会话，不走网关），`fetch failed` 是
  那条直连链路自己的网络失败，与原地回答无关，另案处理。

## 根因分析

接线疏漏 + 类型没兜住：网关的请求类型要求 `position`，但目录适配器一侧的
依赖声明把同一种请求写成了一个没有 `position` 的窄类型，两处各写各的、
谁也不校验谁，组装时字段自然缺席。测试里所有用例都显式传了位置，掩盖了
缺省路径。

## 修复方案

- 目录适配器：调用网关时显式传占位位置 `{turn: 0, step: 0}`（模型的请求
  选项本就不带步号），并把 `position` 写进依赖声明，让类型两端对齐。
- 网关：位置缺席时降级为同一占位值而不是崩掉回合——占位即可，因为网关
  不写任何持久内容，落位由原生循环负责。
- 回归测试两条：目录适配器实测送出的位置字段；网关在位置缺席时照常完成
  一次回答且运行器读到 0。

  作答、增量）通过。
- 重启 3081 启动日志干净。
