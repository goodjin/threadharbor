# 会话状态按「模型往返」细化：发送 / 已发送等待 / 已收到响应

## 问题描述

- 日期: 2026-09-30
- 严重程度: Low（体验）
- 影响范围: 会话页顶部的回合状态横幅与转录尾行

一轮对话进行中，状态只有「思考中 / 工具执行中 / 正在处理工具结果 / 正在生成回复」
四档。工具结果回传后那句「正在处理工具结果 —— Agent 已收到工具结果，正在继续处理」
看不出现在到底处在哪个环节：请求发出去了没有、是在等模型还是模型已经在回答。

## 根因分析

状态机只按「最后一条记录的类型」分档，没有表达「模型往返」这个用户真正关心的
生命周期。可观测的边界其实都在：

1. 请求发出（浏览器→网关→hostd 准入）——真实存在，原来只在第一轮可见；
2. 工具结果落进 journal——这就是下一轮请求的发出时刻，原来被归成
   「正在处理工具结果」这种含糊说法；
3. 模型开始回答（出现 reasoning / 文本 / 工具调用行）——原来直接跳到
   思考中/生成中，不说明「响应已收到」；
4. 每个阶段停留多久——状态里没有任何时间信息，用户无法区分「正常等待」
   和「卡住了」。

## 修复方案

按「模型往返」重组运行中的状态（全部由现有信号推导，无协议改动）：

| 阶段 | 触发条件 | 显示 |
|---|---|---|
| 正在发送请求 | 请求 RPC 在途 | 正在把请求发送给远程 Agent，发送完成后自动开始等待模型响应。已发送 N 秒 |
| 等待模型响应（第 1 轮） | 请求已送达，尚无任何模型输出 | 请求已发送完成，正在等待模型返回第一个响应。已等待 N 秒 |
| 等待模型响应（第 k 轮） | 工具结果刚落账 | 第 k 轮请求已发出：工具结果已发回模型，正在等待下一个响应。已等待 N 秒 |
| 思考中 | 最后一条是推理输出 | 已收到模型响应，正在思考。已持续 N 秒 |
| 工具执行中 | 最后一条是工具调用 | 工具标题 · 已运行 N 秒 |
| 正在生成回复 | 最后一条是正文输出 | 已收到模型响应，正在输出内容。已持续 N 秒 |

每个进行中的阶段都带秒级运行时长（复用回合期间的每秒活动时钟）：

- 发送计时从浏览器提交时刻起（`progress.startedAt`）；
- 「正在连接 Agent」横幅同样显示「已尝试 N 秒」——这正是当初 hostd 掉线时
  最需要看到的数字；
- 等待确认（权限）从提问落账时刻起；
- 思考/生成的时长按「同类型连续段」计：工具轮之后的新思考段重新起表，
  并行加入的工具调用不重置批次计时（从第一个调用起算）。

配套调整：

- 等待超过 30 秒的长上下文提示从「仅第一轮」放宽到所有轮次（工具轮之后的长静默
  同样多半是预填充）。
- 只有状态行（如「远程轮次运行中」）没有模型输出时，按「等待模型响应」显示，
  不再误显示「正在生成回复」。
- 网关的进度文案对齐同一套词汇（「请求已送达远程 Agent，等待模型响应」）。

Agent 内部对模型的网络调用本身不可观测（对各 Agent 后端一视同仁），所以中间轮次
不假装有「发送给模型中」的阶段：工具结果落账即视为下一轮请求已发出。

## 验证步骤

1. `npx vitest run`：502 条全绿（含新增「shows each model round-trip」与
   「shows a per-stage elapsed timer on every ongoing stage」用例）。
2. `npx tsc -b tsconfig.json`：退出码 0。
3. 产物断言钉住新文案（等待模型响应 / 请求已发送完成 / 工具结果已发回模型 /
   已收到模型响应 / 已持续 / 已发送 / 已尝试 / 已运行）。
4. 重启 3081 后发起一轮带工具调用的对话，观察横幅依次走完
   发送 → 等待（第 1 轮）→ 思考/工具 → 等待（第 2 轮）→ 生成回复，
   每档都带递增的秒数。
