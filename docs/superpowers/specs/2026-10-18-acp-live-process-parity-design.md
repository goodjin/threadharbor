## 问题：过程展现与原生 DSH 的三层落差

用户反馈：codex-acp 回合进行中的思考、工具调用、文本渲染与原生差别很大，看不到全过程。
对照参考实现逐层核实，根因三条，两条接入路径（预设接管、网关就地回答）共同命中：

1. **思考与正文被打乱**。实时流只给整个外部回合留两个块位：所有思考一个块、所有正文
   一个块（`stream.ts` 的按类槽位 + `gateway.ts` `GatewayChunkStream` 的按类 Map）。
   而真实回合里「文本→工具→文本→工具→文本」交错多次（见下方捕获证据），于是中途新
   思考窜到已刷出正文上方、几段正文被拼成一段，时间线不可读。原生模型流是每个片段
   一个块、按到达顺序出场（`dsh-llm` `StreamChunk`：block-start/delta/block-end）。
2. **工具卡片全程空转**。开卡实时（runner `writeOpeningCard`），但结果只由回合末投影
   落盘——为实时结果准备的 `projectTurnIncremental` 从未接线。原生是每个工具做完即出
   结果。长回合表现为一排无输出卡片挂数分钟后一次性全出。
3. **整个外部回合压成一个 DSH 步骤**。原生一个回合多步骤，客户端「过程折叠、最终答案
   单独展示」（`turn-process.ts` 以「最后一步的无工具调用消息」为答案锚点）依赖多步骤
   结构；单步骤形状下这套体验不存在。

## 决策（已拍板）

1. **接管路径做结构性重做**：一个外部回合按「段落」投影为多个 DSH 步骤，步骤边界由
   原生循环自己写（替换步骤返回「继续」即再被调用，参考 `agent.ts:296-364` 回合循环；
   `followup` 走 next-turn 队列、不进 next-step（`agent.ts:154-173`），段落迭代不受
   用户插话干扰）。DSH 宿主与 web 客户端零改动。
2. **网关路径同步升级到共享修正**（流块按真实顺序 + 工具结果实时落盘），保持单步骤
   ——一次模型请求只占一个步骤号，多步骤在此路径不适用。
3. **直接切换**，不加配置开关；旧会话日志不受影响，只改新回合写法。
4. **验收双路径**：3081 实例（只经 `~/bin/dsh-web-3081` 操作）上，接管会话与网关就地
   回答各跑一轮真实 codex 回合。

已排除的替代方案：插件自写内层步骤边界（与循环自己的 step/end 撞车）；一个步骤写多条
消息（会话视图每步只保留最后一条消息，前面的消失——`projection.ts` 既有注释在案）。

## 机制

### 1. 分段器（dsh-acp-agent 新增纯逻辑）

输入为帧流（方言归一后的 `session/update`），输出「段落闭合」信号。规则：

- 段内至少一个工具调用收尾（completed/failed）**且**段内开过的调用全部收尾 **且** 又
  到达新的非空思考/正文增量 → 当前段闭合，该增量属于新段；
- `session/prompt` 应答到达（成功或失败）→ 当前段作为末段闭合；
- 工具连工具、中间无新文本 → 同一段（对应原生「一条消息带多个工具调用」）；
- 纯聊天回合（无工具）→ 单段，行为等同现状；
- 杂讯帧（usage_update 等）不参与切段；
- 子代理/异步任务的合成卡片不切段：出生段开卡（现状），收尾帧到达即写结果；回合结束
  仍未收尾的照旧写 `[still running]`（现有 stillRunningText）。

闭合时机说明：段 k 的落盘发生在段 k+1 的首个增量到达时（晚一个增量，这是「不知道后面
还会不会连开工具」的诚实代价），该增量进入段 k+1 的流。

### 2. 接管路径：一个段落一个步骤（runner/dispatch/entry）

- `AcpPresetBinding` 增加按段驱动的能力（`runSteps`）：每次调用消费一个闭合段、用当次
  `agent/pre-step` 宣布的步骤号（step-position 现有机制）投影落盘，返回 `null` 表示
  继续；末段返回真实结束原因。现有 `run()` 保留给网关路径（内部同样分段，但一次调用
  跑完全部段落）。分段器、开卡、实时结果、中止旗标等核心共用。
- 首段调用独占的职责：用户消息落盘、模型选择（turnModel）、历史重放/primer。后续段
  调用跳过，避免把循环塞进来的运行时上下文当新提问重复写。
- 实时流每段开一次（`turn.openStream` 每次调用新建 attempt，计数器照旧全程递增），
  与原生「每次模型调用一个流」一致；段落消息内嵌该段的紧凑流记录，刷新回放不变形。
- 用量：codex 只在回合应答报用量 → 只挂在末段消息上（现有 writableUsage 门槛不变）。
- 每段落盘形状（与现状同构，只是分布到各步骤）：开卡公告+卡片（段内实时）→ 段消息
  （该段思考+正文，实时已写卡的 tool-call 块照旧剥离）→ 段内未实时写的卡片+结果补写。
- 段写盘失败：按现有回合末写失败语义抛给循环，回合以错误收场，前几段已在档（与原生
  中途失败同形）。

### 3. 共享修正一：流块按真实顺序（stream.ts / gateway.ts）

- `AcpAssistantStream` 与 `GatewayChunkStream` 的按类槽位改为**换向开块**：思考与正文
  一换向即分配下一个块号，同类增量续写当前块。原生适配器即此行为；客户端
  `PartialAccumulator` 按块号折叠，天然支持。
- 紧凑流记录（StreamRecord 的 index 字段）随块号如实记录，持久回放与直播一致。

### 4. 共享修正二：工具结果实时落盘（runner + projection）

- 工具收尾帧到达即写结果事件（经会话现有 writer，按 `turn:callId` 配对卡片），不再
  攒到段末/回合末；段末投影跳过已实时写过的卡片与结果（现有 written-set 从卡片扩到
  卡片+结果）。
- 网关路径同理：实时开卡（现状）+ 实时结果（新增）；回合末只补写没赶上实时的残余
  （实时写失败回退、spawned 未收尾卡片），**不写任何正文消息**——正文由原生循环从
  chunk 流自组装，避免文本双写与派生历史重复。

### 5. 网关路径边界

- 保持单步骤：段落只影响流块划分与结果落盘时机；循环在流结束后写的答案消息仍是该步
  最后一条消息，答案锚点与折叠展示不受影响。
- 静默看门狗、总上限、停止宽限、静默提示等（2026-10-16 规格引入）全部不动。

### 6. 出错与中止

- 中止：进行中的段照现状「写已到内容、以中止收场」，后续帧丢弃（现有 aborted 旗标），
  该次 runSteps 调用返回中止原因，循环收回合。
- 首段 open/prompt 失败：现有 failureEndOf 分类路径不变。
- 回合中途 reply 失败：末段照常投影已到内容，结束原因为分类错误。

## 兼容性

- 旧会话日志零影响；新回合写出的就是原生多步骤回合形状，回放、分叉、导出走原生路径。
- `turn:callId` 配对键跨步骤有效（content-writer 现有键含回合号）。
- 中途直播时段落流未闭合时，段内先到的工具卡片位置可能先于流块收尾——段闭合后持久
  消息落位，顺序即精确（与原生「消息先于其工具卡片」一致）。

## 测试

- **分段器单测**：直接吃三家真实捕获帧（`tests/fixtures/captured-frames.json`、
  `captured-subagent-frames.json`）断言切分段落；边界用例：无工具、工具后无新文本、
  并行工具、纯杂讯。
- **runSteps 单测**（假循环反复调替换步骤）：多次调用推进、首段独占职责、各段步骤号、
  实时结果与剥离、中止半段、用量只在末段。
- **流单测**：换向开块（两个流类各自）、紧凑记录的块号、end.index 语义不变。
- **网关单测**：实时结果经 tool-only writer、无正文双写、回合末残余补写、看门狗测试
  保持绿。
- **活测**：现有 `THREADHARBOR_LIVE_ACP` 套件保持通过；接管路径新增多步骤断言。
- **验收（用户已拍板双路径）**：3081 实例跑真实 codex 回合，核对过程展现（思考/正文
  按时间线交错、工具做完即出结果、过程折叠与答案锚点）及刷新后回放一致。

## 不做（本轮非目标）

- 改 DSH 宿主与 web 客户端。
- 网关路径多步骤（结构上不可能）。
- 子代理内容的深度投影（维持合成卡片语义）。
- 配置开关 / 双轨行为。
- zcode 路径。
