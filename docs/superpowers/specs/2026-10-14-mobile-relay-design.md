# 手机入口中转方案（云主机 tencent01 聚合）

- 日期：2026-10-14
- 状态：待审
- 前置交付：[手机端独立入口设计](2026-10-14-mobile-entry-design.md)（已上线，各机自伺服 + tailnet 直连）
- 参考事实核对：DSH 参考实现 `reference/deepseek-harness` @ 5badb15009，2026-10-14

## 1. 目标与非目标

**目标**：手机不装 Tailscale，只用浏览器经公网访问一台云主机（tencent01），在一个入口里看到 tailnet 上所有机器的会话，并能读历史、发消息、批权限、停回合。

**非目标**：不做 APK/PWA 封装；不做后台推送通知；不做跨机器会话迁移；不做多用户与权限分级；不替换已上线的各机直连方案。

## 2. 已定决策

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 手机为何不用 Tailscale | 三条同时成立：与 Clash 抢 VPN 通道、不愿手机进 tailnet、手机网络连不上协调服务 | 手机退化成普通公网浏览器 |
| D2 | 云主机如何回到各机 | **数据面走 SSH 本地转发；Tailscale 只做发现**（对端枚举与在线状态） | 实测各机 DSH 只监听回环、tailnet 上无服务且未信任 tailnet 名字；SSH 那条路本来就是取凭据要走的 |
| D3 | 入口形态 | 单入口 + 跨机聚合 | 一处看全部，四个动作都在一个页面 |
| D4 | 凭据模型 | 云主机集中持有各机凭据 | 实现最直接，撤销口径单一 |
| D5 | 公网入口 | 已有域名 + 正规证书 | 手机首访无证书警告 |
| D6 | 与旧方案关系 | 并存，云主机为主入口，旧方案作退路 | 云主机不可用时仍有路可走 |
| D7 | 手机可选机器 | tailnet 对端中探测到跑 DSH 的，自动列出 | 新增机器零配置 |
| D8 | 审批归属 | 先到先得（规则不变） | 桌面在时手机批了，桌面横幅变「已在别处处理」 |
| D9 | 跨机接法 | 常驻事件流 + 按需 HTTP 转发 | 唯一能保持审批实时弹出的接法 |
| D10 | 凭据来源 | 云主机经 SSH 自动读各机启动网址 | 免手工维护 |

## 3. 拓扑与数据流

```
手机浏览器 ──公网 HTTPS(域名+证书)──▶ tencent01: DSH + dsh-mobile-relay
                                              │  ① 主机清单：tailnet 对端（Tailscale 发现）
                                              │     + 隧道内 hello 探测（在跑 DSH 的才列）
                                              │  ② 每台机器一条 SSH 本地转发；持各机 cookie，
                                              │     POST /api/* 按需转发
                                              │  ③ 每机常驻一条 WS（经隧道），事件汇流给手机
                                              └──SSH（私网/公网均可）──▶ 各机 127.0.0.1:<dsh 端口>
```

手机上只有一条出站链路（到云主机）。各机 DSH 继续只监听回环、不对 tailnet 暴露任何东西；云主机到各机的全部流量都走在 SSH 里。Tailscale 在云主机上只用于发现（有哪些对端、在线与否）。

**实测事实（2026-10-14）**：

- 各机 DSH 监听回环地址（例：本机日常实例 127.0.0.1:3081），tailnet 地址上无服务；该实例启动未带 `--trusted-host`，`tailscale serve` 无配置。
- tencent01 经 tailnet 可连本机 22 端口；tencent01 已装并在跑 Tailscale（100.84.120.35），Node 为 v20.20.2（仓库要求 ^22.19.0 || >=24，部署前需升级），尚未安装 DSH。
- 回环 authority 被官方信任栅栏直接放行（`api-request-trust.ts:103` 的 `isLoopbackHostname` 分支），因此隧道后端无需 `--trusted-host`。

## 4. 组件

新增宿主侧插件 `packages/dsh-mobile-relay`（组合行 `threadharbor-mobile-relay`，注入 `['webServer','connection']`）：

| 模块 | 职责 |
|---|---|
| `hosts.ts` | tailnet 对端枚举（复用 `dsh-host-federation/tailscale` 的 `queryTailscalePeers`）+ 隧道内 hello 探测，产出主机清单 |
| `tunnels.ts` | 每台机器一条 SSH 本地转发（复用 `DshSshManager.ensureTunnel`）；本地端口固定分配并持久化 |
| `credentials.ts` | 各机 cookie 的获取、持久化、失效重取（SSH 读启动网址 → 经隧道换 cookie） |
| `machine-client.ts` | 对单机的 RPC 调用与 WS 事件流；重连、401 自愈 |
| `hub-routes.ts` | 对手机暴露的 `/threadharbor/relay/*` 接口与事件 WS |
| `mobile/` | 复用已上线手机页的壳与视图，加「机器」维度 |

复用不重写：静态壳与路由前缀沿用 `dsh-mobile-entry` 的做法（同一套 `MOBILE_PREFIX` 约定、配对流程、`hello` 探测）；手机页 `app.js`/`views.js`/`wire.js` 在其基础上扩展。

## 5. 鉴权与凭据生命周期（已核对官方实现）

**官方行为（事实）**：

- `/api/*` 与 `/api/remote.mux` 的准入是「可信 Host 栅栏 + 已认证 cookie」两级（`packages/client/connection/src/rpc-host.ts` `requestRejection`/`admit`）。cookie 缺失或不合法即 401，Host 不可信即 403。
- 凭据只认 cookie。进程启动令牌不直接用于 API（`browser-auth.ts` `isAuthenticated` 只读 cookie）。
- 换 cookie 的唯一入口是 `GET /` 带 `?token=`（`authorizeIndex`），成功返回 303 到 `./`，凭据与请求的 Host 绑定。
- **没有 Origin 头是可以接受的**（`api-request-trust.ts`：Host 栅栏通过后，Origin 缺失直接放行）→ 服务端可代表浏览器调用。
- 启动令牌每次进程激活随机生成、不落盘（`processLaunchToken`）；cookie 签名密钥是持久的（`BrowserAuth.create` → `initializeSecret`），cookie 有效期由 `cookieMaxAgeDays` 决定（现有配对用 30 天）。

**由此得出的机制**：

1. 云主机对每台机器开一条 SSH 本地转发（本地端口固定分配并持久化），把该机的回环 DSH 端口映射到云主机本地端口 `L`；authority 即 `127.0.0.1:L`（回环默认受信，无需各机改配置）。
2. 云主机经同一条 SSH 读该机 DSH 启动日志里的启动网址（部署流程解析的 `LAUNCH_URL=` 标记，取最后一行），拿到本次激活的令牌。
3. `GET http://127.0.0.1:L/?token=<令牌>` → 取 `Set-Cookie` → 存为该机凭据。
4. 该 cookie 绑定 authority（`127.0.0.1:L`），后续所有请求与 WS 升级都用同一 authority；端口一经分配即固定（端口变了凭据即失效）。
5. cookie 落盘到云主机 DSH 家目录（权限 0700/0600），云主机重启后直接恢复，不必重取。
6. 任一请求返回 401 → 判定凭据失效 → 经 SSH 重读启动网址换新 cookie → 重试一次；再失败则该机标为「凭据需更新」并在手机上如实说明，不静默降级。
7. 因 cookie 有效期约 30 天，SSH 重读是低频事件；SSH 不通时该机降级为只读历史（用最后快照并标注时间）。

**隧道与指纹**：SSH 连接信息（目标、用户、端口、密钥）来自云主机配置；主机指纹复用联邦包同一份 known_hosts，未登记的机器按现有流程报「需确认指纹」，不在无人值守时自动信任。

## 6. 机器清单

云主机列 tailnet 对端（发现） → 对每台对端开隧道后并发探测隧道口的 `/threadharbor/mobile/hello` → 探测通过的列为可选机器。未探测到 DSH 的对端不出现（路由器/NAS 等天然被排除）。清单缓存沿用已上线的 5 秒级策略，探测超时 2 秒。

机器标识用 tailnet DNS 名（稳定、页面可读），与 SSH 配置、Tailscale 对端三者按名字对齐。

## 7. 跨机调用与事件转发

**调用面**（已由前一阶段探针钉死）：会话列表、翻历史、发消息、停回合走官方 RPC（`POST /api/<endpoint>`，信封 `{method,payload,rpcId}`，`payload` 内嵌 `args`）；事件与审批走 `/api/remote.mux` 的 WS。

**转发面**（对手机）：

| 接口 | 用途 |
|---|---|
| `GET /threadharbor/relay/hosts` | 主机清单（含在线/凭据状态） |
| `GET /threadharbor/relay/hosts/:hostId/sessions` | 该机会话列表 |
| `GET /threadharbor/relay/hosts/:hostId/sessions/:sid/messages` | 历史分页 |
| `POST /threadharbor/relay/hosts/:hostId/sessions/:sid/prompt` | 发消息 |
| `POST /threadharbor/relay/hosts/:hostId/sessions/:sid/cancel` | 停回合 |
| `WS /threadharbor/relay/events` | 手机 ↔ 云主机单条事件流（汇总各机） |

**事件汇流**：云主机对每台在线机器常驻一条 WS，把事件加上机器标识后广播给所有连着的手机。手机应答审批时，云主机把应答转给对应机器的那条 WS；机器侧仍是「先应答生效」，若桌面已先应答，手机收到 `cancel` 结果并显示「已在别处处理」。

**规模**：连接数 = 机器数 ×1 + 手机数 ×1，个人规模（几台机器）下无压力。

## 8. 手机页改动

- 首屏由「会话列表」改为「机器选择」；选定机器后进入该机的会话列表，顶部有当前机器与切换按钮。
- 审批横幅、会话条目都带机器标识（跨机汇总时不能混淆来源）。
- 错误口径区分两类来源：云主机侧（机器离线、凭据需更新、云主机与 tailnet 断开）与机器侧（机器返回的原文）。
- 会话历史分页、发送中状态、待答审批禁用等行为沿用已上线实现（其并发竞态防护已在上一阶段处理）。

## 9. 安全姿态与取舍

**接受的代价**：云主机持有全部机器的操作凭据，是高价值目标。缓解：凭据只存云主机家目录（0700/0600）、任何日志不打印凭据与令牌、手机永远拿不到各机凭据、撤销 = 云主机删该机凭据（30 天 cookie 过期或主动清空即失效）。

**边界**：

- 云主机对外只暴露 HTTPS，域名证书正规，手机首访无警告。
- 云主机 DSH 需把公网域名列入 `--trusted-host`，`mobileOrigin` 设为该域名（沿用已上线的配置与校验）。
- 手机配对走已上线的二维码流程，凭证只对云主机生效。
- 各机 DSH 保持只监听回环、**不需要**新增 `tailscale serve` 或 `--trusted-host`；云主机到各机的流量全在 SSH 隧道内。
- 云主机被攻破 ≈ 全部机器会话被接管——这是本方案与「各机各自签发」的关键差异，写进文档明示。

**不做**：不把各机凭据下发给手机；不做浏览器端可见的令牌透传；不记录会话内容到云主机磁盘（仅内存 + 事件流）。

## 10. 并存与退路

已上线的「各机自伺服 + tailnet 直连」保留原样。云主机整体不可用时，手机仍可用旧方案（前提是手机网络能直连 tailnet）。两者互不依赖：旧方案不依赖云主机，云主机方案不依赖旧的静态服务部署方式。

## 11. tencent01 准备清单

1. 装 Tailscale，加入 tailnet（**已完成**：100.84.120.35，TUN 在跑），确认能看到各机对端。
2. Node 升级到 22.19+ 或 24（现为 v20.20.2，低于仓库要求）。
3. 域名与证书就位（已有），只暴露 443。
4. 装 DSH + ThreadHarbor（含新插件），启动时带 `--trusted-host <公网域名>`。
5. 配 `mobileOrigin = https://<公网域名>`。
6. 配置云主机 → 各机的 SSH 凭据（密钥/端口/用户），并把密钥加入各机授权列表。
7. 手机扫云主机页面上的二维码完成配对。

## 12. 失败与降级矩阵

| 情况 | 表现 | 手机上的说法 |
|---|---|---|
| 某机离线 | 该机无 WS，历史用最后快照 | 「该机器当前离线，显示的是最后一次读到的内容（时间）」 |
| 某机 cookie 失效 | 自动 SSH 重读 + 重换；失败则标脏 | 「凭据需更新」并给出处理指引 |
| 某机 SSH 隧道断 | 该机标离线、WS 重连 | 「连不上这台机器（SSH 通道断开）」 |
| 某机指纹未登记 | 不自动信任，不建隧道 | 「这台机器的 SSH 指纹未确认」 |
| 云主机与 tailnet 断开 | 仍能按已登记机器经 SSH 访问；仅新发现失效 | 「暂时发现不了新机器」 |
| 云主机重启 | 从磁盘恢复 cookie 并重连 | 短暂「正在恢复连接」 |
| 某机 DSH 版本不匹配 | 该机调用返回明确错误 | 「这台机器的接口与手机页不匹配」 |

## 13. 阶段与验收

**阶段 0（先验证再建）**：在 tencent01 上实测——① 宿主代码可用的 WebSocket 客户端与 Node 版本（升到 22.19+/24 后）；② SSH 隧道 + 服务端换 cookie 的完整链路（命令级复现：开隧道 → 读启动网址 → 换 cookie → 调会话列表成功）；③ 云主机经 SSH 读各机启动日志取令牌可行；④ tailnet 对端枚举与隧道口 hello 探测；⑤ 手机经公网域名访问云主机页面与配对。任一项不成立先调整方案。

**阶段 1**：云主机侧（清单、凭据、单机客户端、转发接口、事件汇流）。
**阶段 2**：手机页机器维度。
**阶段 3**：文档与脚本（tencent01 准备、手机侧排查三步：通道占用 → 直连规则 → 证书信任）。
**阶段 4**：真机验收（手机走查、整机重启后凭据自愈、真实审批闭环）。

验收标准：手机经公网域名完成「选机器 → 看会话 → 读历史 → 发消息 → 批权限 → 停回合」全链路；断网/重启后能自愈或如实说明；凭据不出现在任何日志。

## 14. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| SSH 是承重路径（隧道与凭据都靠它） | SSH 一断，该机全不可用 | 阶段 0 验证；不可达时如实标注并给处理指引，不静默 |
| 各机需云主机 SSH 可达且密钥已授权 | 新机器接入要配一次授权 | 准备清单里写明；未授权的机器不进清单 |
| 笔记本类机器会休眠 | 隧道频繁断、WS 重连 | 离线态如实标注，不做假在线 |
| 云主机成为单点 | 全部手机入口不可用 | 旧方案并存作退路 |
| 本地端口与凭据绑定 | 端口重分配会让凭据集体失效 | 端口固定分配并持久化；重分配后强制重换凭据 |
| 跨机转发改动官方调用面 | 版本漂移导致某机失效 | 错误口径按机器区分，阶段 0 记录核对时间 |

## 15. 开放问题（实施期确认）

- 宿主侧 WS 客户端：需能带 Cookie 头升级连接（浏览器与 Node 内置 WebSocket 都不支持自定义头），倾向用 `ws`（DSH 自身依赖 ^8.21.0，工作区已可离线安装）；阶段 0 出结论后定。
- 手机页「先选机器再看会话」是否需要在多机场景提供聚合列表（一次看全部机器的最近会话）——按当前决策先做选机，聚合列表列为可选增强。
- 云主机家目录凭据文件是否需要额外加密（默认依赖 0700/0600 文件权限）。
