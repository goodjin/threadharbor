# 设计：多会话共用一个 Agent 连接

## 目标

hostd 现在是**一个远程会话起一个后端进程**。实测 dsh 后端常驻约 435 MB，于是会话数 N 就是 N 份内存。改成同一台机器上同一个 Agent 只连一次，所有会话共用。

## 依据

实测，不是推断。多会话接在**同一个** dsh 后端上，五个会话同时提问：

| 观测项 | 结果 |
|---|---|
| 五个会话的后端进程数 | 1 |
| 每个会话的原生会话 id | 五个，互不相同 |
| 五个会话是否都拿到自己的回答 | 是，全部 |
| 建第一个会话 | 299 ms |
| 每加一个会话 | 20–22 ms |
| 一个会话时后端常驻内存 | 420 MB |
| 五个会话时后端常驻内存 | 461 MB |

今天是每加一个会话 435 MB：五个会话约 2.1 GB，改完约 0.46 GB，且会话再多也不按倍数涨（每加一个会话约 10 MB）。

## 桥接是模块，不是进程

桥接是 hostd 里的一个模块，**不单独起进程**。曾经设计成独立进程，理由是"hostd 重启不该打断远程会话"。这个理由不成立：

- 机器层面的事件（休眠、重启）对 hostd 和独立进程一视同仁，隔离在这里一分钱都不值。
- 单人部署，两个会话不会共用一个实例，不存在"升级时踢掉别人正在生成的回合"。

省掉独立进程还顺带删掉了一整类现存缺陷。这些缺陷全都是"hostd 只能通过一个进程间接操作一个会话"逼出来的：

- 订阅分发只认第一个订阅者，挂在同一 hold 上的第二个会话收不到自己的帧
- 空闲回收混用了两个层级的键，子会话空闲会把父会话的后端一起回收
- `session.adopt` 让多个会话共享一个 holdId，这条路完全没有测试

进程内设计不是少一层封装，是把这些机制**删掉**。

## 连接归桥接，会话归会话

同一个 Agent 的所有会话共用一条后端连接。桥接（进程级）持有：后端子进程、一次握手、收到的帧。AgentSession（会话级）持有：journal、序号、原生会话 id、准入去重、提示词队列、等待者、合帧器。

**握手归桥接所有。** 连接在任何会话存在之前就已经在了，没有会话可以塞握手帧。握手帧不写进任何会话的 journal。

**收到一帧，交给谁**，三条规则，不猜：

1. 带请求 id 的 → 找当初发起它的那个会话；
2. 带 `params.sessionId` 的 → 找原生会话 id 对应的那个会话；
3. 两条都不匹配（后端挂了这类事件）→ 给所有会话各记一份，因为每个会话的记录都得写明"我这边的后端没了"。

帧本身原样过。**桥接不做协议转换。** 统一协议是 ACP 自己给的，不在这里。唯一的归一化是回合完成事件：有后端自己会发，有的不会，桥接替不发的补一条——是"保证大家都有同一个事件"，不是翻译。

不归一化数据是刻意的：journal 存原样帧，解释成什么样是下游投影的事。usage、工具元信息、token 统计各家字段不同，一旦在桥接这层抹平就永久丢了。

## 恢复

- 正常路径走 `session/resume`（dsh）或 `session/load`（其余）。这是各 Agent 的基本功能：读回 Agent 自己写好的会话存储，拿到的是模型真正的上下文，不是引用的文字。
- **恢复失败不许沉默。** 原来是 catch 掉然后悄悄开一个新会话，用户看着完整的历史记录以为 Agent 还记得——记忆确实丢了，但没人知道。现在直接让这次挂接失败并把原因带出来，让用户自己决定要不要重开。把"记忆丢了"变成一次可见的失败，好过让它伪装成正常。
- **不建重放引擎。** 能放原生格式的消息数组就在 Agent 自己的存储里，而 resume 干的就是读它。手工重放要自己写进 Agent 内部格式，严格更脆——Agent 一升级就得跟着改。保留为明确标注的最后手段，暂不实现。
- 转录记录本身有上限（按条数和字节裁剪），老会话早期内容可能已被裁掉，这种情况要如实告知，不能假装完整。

## 单会话重启

进程没了，杀死一个会话就是杀死所有人的会话。所以 `session.restart` 不再杀任何进程，改成只清这个会话自己的状态：先给还在跑的回合发一个取消，再把这个会话槽拆掉重开。卡死的是会话槽（提示词队列、等待者、没收完的分片），不是 Agent 本身。

这样比原来的行为更准也更安全：原来重启会先杀掉 Agent，再指望 resume 把它记的东西找回来；现在 Agent 一直活着，上下文原封不动。

## 进程收尾

实测：父进程被强杀后，codex 0.02 秒、dsh 0.30 秒、claude 0.81 秒退出。原因不是进程树机制（Unix 下父进程死了子进程一律不自动杀），是 stdio 管道关闭后这些程序把 stdin 结束当作退出信号。

- 正常退出（发版、Ctrl-C）：主动关掉子进程输入管道再等它退，最干净。
- 强杀或崩溃：不用管，管道一关自己就退。
- 启动时扫一遍残留：降级成兜底，防的是以后接入的新后端不认这个规矩。不是热路径。

**但实测推翻了"关掉输入管道就等于收干净了"这个前提。** 真实的坑在这里：dsh 规定一个会话只能被一个活着的进程持有（`already owned by an active write handle`）。而一个正在流式输出的 dsh 不会立刻理会输入端的 EOF——实测里空闲的 dsh 0.3 秒就退，忙着的那个能活过好几分钟。

于是形成了一个死循环：hostd 被停掉时如果只关监听端口，dsh 会连同 hostd 一起活下来 → 下一个 hostd 恢复会话时被拒 → 用户只能重开 → 重开又起新的 dsh → 旧的还占着。每重启一轮就多一个占位的进程，会话被锁得死死的。

现在停 hostd 的顺序是：先停所有 Agent（SIGTERM，等 2 秒，不行就 SIGKILL），再关 ws，再关监听端口；收到停止信号后必须真的退出，最多等 15 秒就硬退。**端口释放不能当作停干净的证据**——监听端口是最先关的，Agent 是在它之后才死的。这条用一个"关掉之后 Agent 必须消失"的测试钉住。

grok 连的是共享服务，不是子进程，不存在这个问题。

## 帧处理不许抛

以前会话簿记的 bug 最多弄坏一个 Agent；它在 hostd 里，一个未捕获异常会连带打挂网关前端。帧处理整段兜住，就地消化，不往上抛。

## 测试

必须新增的断言（改之前一条都没有）：

- 零会话时就完成握手，且整个连接只握手一次
- 多个会话共用一条连接、一次握手、共享同一个后端进程
- 路由不串：每个会话只拿到自己的帧，各自序号从 1 开始各自连续
- 准入去重、提示词排队、取消，都是按会话分开生效的
- 拆掉一个会话，其余会话照常推送
- 等待者只被自己那个会话的推进唤醒
- 后端挂掉，所有会话各自都记到了
- 某会话写不进 journal 时，桥接照常服务，并把这个失败暴露出来
- 回合完成事件的补齐：正常返回、返回错误、权限请求卡住，都是三种不同形状
- journal 裁剪后要如实报缺口，不能假装完整
- `session.adopt` 现在第一次有了测试：两个会话挂在同一个 Agent 会话上，各有各的记录
- Agent 恢复失败时挂接必须报错，不能悄悄开个新的

删掉 `hold-worker.spec.ts`（21 个用例）之前先把其中只有它覆盖的行为搬到桥接测试上：回合完成事件的合成、权限请求把回合卡住、journal 保留策略的裁剪。替身也重写了：原来那个"一进程一 journal"的假 worker 换成了会握手的假 Agent，`hostd-ws` 的假后端从按 holdId 建模改成按会话建模。

## 改完之后的实测

同一台机器、同一份真实 dsh 装、真实的 hostd 代码，开 5 个会话：

| 观测项 | 改之前 | 改之后 |
|---|---|---|
| 会话数 | 5 | 5 |
| dsh 进程数 | 5（外加 5 个 worker 进程） | **1** |
| dsh 常驻内存 | 约 2.1 GB | **440 MB** |
| 每多一个会话 | 约 435 MB | **约 9 MB** |
| 建第一个会话 | 约 300 ms | 740 ms（含起进程） |
| 每加一个会话 | 一整个进程 | 20–23 ms |
| 5 个会话同时提问 | — | 1 ms 内全部受理，5/5 都拿到回答 |
| 跑完 5 个回合后 | — | 1 个进程，485 MB |

握手这一次成本摊到了后面所有会话上，所以第一个会话比原来慢一点（多了一次握手），之后每个会话都是几十毫秒。5 个会话省下约 1.7 GB，而且会话再多也不按倍数涨。

## 遗留

`holdId` 原本指"一个 hold worker 进程"，现在指"桥接里的一个会话"，名字已不准确。留着不改是为了磁盘上 `holds/<holdId>/` 的布局、会话记录和恢复逻辑都能原样继续。要改名得单开一次。

## 重开时的上下文

重开分三种情况，**它们的可信度完全不同，所以必须分开说**：

| 情况 | Agent 拿到的是什么 | 说法 |
| --- | --- | --- |
| 原生会话能恢复 | 它自己的记忆，完整的 | 正常 |
| 原生会话没了，但有对话记录 | 网关把之前的对话整理成文字发过去 | 明确说是重建的 |
| 原生会话没了，也没有记录 | 什么都没有 | 报错，不假装记得 |

第三种是关键。静悄悄地起一个空白会话，比直接报错坏得多：用户会读到一段完全无视他说过什么的话，还以为是 Agent 理解错了。

第二种是补上的能力。网关本来就存着每一轮对话的投影，所以重开时它把"用户说过什么、Agent 答过什么、做过哪些工具调用"整理成一段文字交给 hostd，hostd 再把它作为第一条消息发给 Agent。这样模型是**读**到了历史，不是**记得**历史——工具调用会以文字形式回来，不能直接重跑。这个区别必须让用户知道，所以 attach 的返回里带了一个来源标记。

整理的时候只留用户和助手的正文，以及每条工具调用的一行摘要。思考过程、用量统计、工具结果全文都被丢掉：它们占预算，又不教给模型任何它需要的东西。超过 8 万字符时只保留最近的部分，并且明确告诉用户开头没了——宁可少给，不能假装给全了。

**用户提问不在 Agent 的记录里**（那是发给它的请求，不是它返回的帧），所以历史必须由网关提供，这条是整条链路成立的前提。

## 序号是游标，游标不能倒退

一条记录里的 `seq` 不只是排序，它同时是读者的游标：界面用"从这个序号之后还有没有新东西"来读。写入的序号一旦低于某个读者已经越过的位置，那些内容对它就等于不存在——不会报错、不会补发，只是永远到不了。

出问题的写法是"从文件最后一行接着往下编"。而文件**不保证是按序号排列的**：重开会把磁盘上的东西重新读一遍，重绑之后到达的帧完全可能落在更早的帧下面。实测里一个会话的序号倒退过 17 次，最大是 3448，文件最后一行却是 3442。

后果比界面显示严重：**重开之后任何失败的回合都是隐形的。** 那一轮的失败帧被写在了游标下面，界面收不到，就一直显示"思考中"——看上去像模型在长上下文里慢慢想，实际上那一轮当场就被拒了。判断卡死不能只看界面，得看进程有没有在干活：CPU 是 0 就说明它什么都没做。

所以新序号要接在**文件里出现过的最大序号**之后，不是最后一行之后。

## "已断开"不等于"坏了"

侧边栏挂红字，本意是提醒用户这个会话需要处理。但一度几乎每一行都在提醒，因为判据站不住：

**第一，hostd 没吭声被当成了回答。** 走 SSH 隧道、45 秒预算，恢复一个 1.76 MB 的会话很容易超预算。超时的含义是"这次没连上"，跟会话本身坏没坏无关——记录还在、历史还能读、host 一恢复就能用。而当时任何一次 attach 失败都会把会话标成断开，而且是**不可恢复的**：后面一切正常，成功的事件同步也不会把它改回去。

所以现在按**错误的含义**分类，而不是按调用者：host 回答了"没有这个会话"，或者连接确实断了（socket 不存在），才叫断开；host 根本没回答（超时、连接中途断），算重连中，��下次调用自己好。

**第二，空闲不是错误。** 大部分会话在大部分时间里都是空闲的——没人在看，就没有活的通道，这是正常状态。只有**正在跑的那一轮被切断**才是错误，而那已经由回合状态单独表达了。所以一个回合已经结束的会话，不该再挂一个红色的通道错误。

两条合起来：侧边栏上真正需要你动手的会话，才会是唯一醒目的那一个。

## 提示自己会先把会话绑上

会话在 Agent 那里是**两半**：一半在进程内存里，一半在磁盘上。hostd 一重启，内存那半就没了，磁盘那半还在——所以它是可恢复的，不是丢了。

危险在于网关不这么看。网关把"通道是开的"记在会话视图里并持久化了；hostd 重启之后这个记录还在，于是网关不觉得需要重新挂接，提示就**直接发进了那个从没听说过这个会话的 Agent**，当场被拒。用户看到的是"本轮执行失败"，而磁盘上文件好好的，看不出任何原因。

所以最后一道防线放在 hostd：**提示是唯一一条绝不能发给"还没被告知过的会话"的帧。** 在受理之前先确认绑定；没有就先把会话恢复出来。这样"没挂接过"就从一个静默的失败，变成了一个能自愈的正常动作。

代价是第一条消息会多花一次恢复的时间（实测在这个会话上是秒级），换来的是不会再出现"文件明明在，却说不认识"。

顺带一条纪律：**任何"我记得它是好的"都不算证据。** 通道状态、绑定标记、游标位置，全都是上一次进程留下的记忆，必须靠一次真实的往返来刷新。这个坑今天在三个地方各犯了一次——通道状态、序号游标、还有这次的绑定。

## 不是我们的会话，就不要写进我们的记录

Agent 自己也会开会话——它派出去的子任务、后台跑的东西。那些帧带着一个本机不认识的会话号。原来的兜底逻辑是"认不出来就广播给所有人"，于是子任务在说什么，逐字进了**每一个**会话的记录里，界面上看着像别人在说话。

广播只对一种情况是对的：**帧里根本没写会话号**。写了、但写的不是我们任何一个，那是 Agent 自己的事，不该进任何人的记录——丢掉，并留下一行说明，让人能看出"Agent 正在跑我们不拥有的会话"。

## 启动时不许相信磁盘上的"通道是开的"

会话视图把通道状态持久化了。进程一重启，什么通道都没了，但磁盘上那个"open"还在。于是网关认为不用重新挂接，用户打开会话、看到完整历史、一行正常，发消息——然后撞上一个从没听说过这个会话的 Agent。

所以启动时把所有"开着的"降级。降到**断开**而不是"建立中"，有两个原因：断开是跟接路径已经知道怎么修的状态，打开会话就会真的重新挂接；而"建立中"会永远停在那里，因为没有任何东西会把它推完。

降级之后实测：重启后 26 个自称开着的会话被降级，跟接循环自己就把能修的修好了（有两个当场回到 open），其余在打开时修。而"打开"这个动作现在真的会触发挂接——之前那 0 次挂接就是这个漏洞的直接后果。

这里还有一条判断上的教训：我第一版降级到了"建立中"，理由听起来没问题（"正在建立"总比"假装开着"诚实），但那会把 26 个会话变成永远转圈的"建立远端…"，是**更难看的谎**。诚实的状态和好用的状态不总是同一个，这个得当场推一遍，不能想当然。
